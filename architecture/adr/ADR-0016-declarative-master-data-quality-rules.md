# ADR-0016 使用声明式白名单规则和自动问题生命周期治理主数据质量

## 背景与问题

医院 HRP 需要持续检查 ERPNext 标准主数据的必填、枚举、长度、格式和引用完整性。若允许管理员录入
SQL、Python 或任意表达式，规则将能够越过权限边界、访问敏感字段、拖垮后台任务，且难以稳定审计。

设计目录原有的 `HRP Data Quality Issue` 是通用可提交单据占位模型，与自动检查产生、自动解决和重开
同一个问题的实际生命周期不符。

## 决策驱动因素

- 标准主数据所有权必须继续属于 ERPNext；
- 规则必须可解释、可审计、可限制资源消耗；
- 字段范围必须服从代码内静态主数据策略；
- 同一规则和记录不得并发产生重复问题；
- 定时检查必须可分页、可重试、可幂等；
- 观察值和规则备注不得进入审计日志或公开响应；
- 不修改 Frappe、ERPNext、Frappe HR，也不创建第二个自研 App。

## 备选方案

1. 允许管理员编写 SQL/Python：灵活，但无法建立可靠的安全、性能和审计边界。
2. 每个字段硬编码独立检查函数：安全，但扩展成本高，重复服务和测试较多。
3. 使用声明式操作符白名单、静态字段策略和固定命名格式，并用自动问题台账承载结果。
4. 每次失败创建新的可提交问题单：保留历史直观，但重复记录多，状态与同一根因割裂。

## 决策

采用方案 3，并为问题生命周期采用“规则 + 目标”单一问题台账。

规则只允许 `Required`、`Allowed Values`、`Maximum Length`、`Named Pattern` 和
`Reference Exists`。`Named Pattern` 只能从代码固定名称中选择，不接受自定义正则。规则参数先经过
大小、键集合、类型和数量校验，再规范化和生成摘要。

问题单改为非提交型、服务专属写入对象。失败时创建或重开，通过时自动解决。确定性 `issue_key` 和
数据库唯一约束共同保护并发。该选择取代设计目录中的通用可提交占位字段，运行时模型与蓝图、字段目录
同步更新。

## 后果

新增常见质量规则无需写业务代码，规则的能力边界保持清晰；不支持复杂跨记录公式和任意脚本。
后续若需要新操作符，必须在公共契约、执行器、资源上限和测试中显式实现。

同一问题的历史通过修订号、发现次数和时间字段聚合，避免重复问题单。详细逐次事件由结构化审计日志
承担；业务表不保存观察值原文。

## 验证与退出条件

- 运行时元数据、蓝图和设计目录字段完全一致；
- 两个 DocType 在 Desk 中只读，直接插入、修改、删除均被拒绝；
- 覆盖五类操作符、参数边界、敏感字段、未知字段和注入输入；
- 覆盖规则创建、幂等重放、无变化、修订冲突和身份不可变；
- 覆盖失败创建、通过解决、再次失败重开和数据库唯一冲突；
- 覆盖组织范围、角色、Guest、真实 HTTP 和缺失幂等键；
- 覆盖每日调度和 200 条稳定分页；
- 审计和公开响应不包含观察值或备注原文。

## 迁移与回滚

升级前备份数据库，运行 `bench migrate` 创建两张表和命名索引。回滚应用版本时保留表、规则、问题和
摘要，不执行破坏性删除。恢复新版本后可继续评估原规则。

## 安全与合规

Guest 永久拒绝，角色校验发生在幂等预留之前。动态标识符来自静态策略，所有记录值使用 SQL 绑定参数。
规则不能执行 SQL、Python、表达式或网络调用；后台任务有固定批量上限。
