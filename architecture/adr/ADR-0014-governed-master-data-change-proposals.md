# ADR-0014 使用静态字段策略和双人复核治理标准主数据变更提案

## 背景与问题

ERPNext 的 `Department`、`Cost Center`、`Item`、`Supplier`、`Warehouse` 由各自标准
控制器拥有。医院仍需要统一提出、复核和追踪这些主数据的新增、修改与停用意图，但任意
DocType/字段写入器会绕过标准控制器、权限和业务校验；在审批时直接修改标准记录，也会把
治理决策与不可控业务副作用耦合在同一事务中。

## 决策驱动因素

- 保持 ERPNext 对标准主数据及其控制器的唯一所有权。
- 只允许经过审查的 DocType、字段和值类型进入申请。
- 提交和批准前都要发现目标记录或组织范围漂移。
- 申请人不能审核自己的申请，且已提交提案不可修改或取消。
- 写服务必须具备角色、幂等、行锁、乐观修订和脱敏审计。
- 不修改 Frappe、ERPNext 或 Frappe HR，不创建第二个自研 App。

## 备选方案

1. 提供通用 DocType 和字段写入 API：扩展快，但无法可靠保证标准控制器和敏感字段边界。
2. 批准时直接调用每个标准控制器：闭环短，但审批失败与业务副作用耦合，回滚和补偿复杂。
3. 每类主数据创建独立审批 DocType：语义最强，但重复状态机、权限和审计实现。
4. 使用静态目标策略、统一字段提案和双人复核，批准仅确认提案。

## 决策

采用方案 4。

`HRP Master Data Domain` 只引用源码注册的五类标准 DocType。策略包含允许操作、允许字段、
值类型、必填项、Link 目标和摘要版本，Desk 中只读。`HRP Master Data Request` 保存组织
范围、操作、目标基线时间、字段当前值和建议值；所有写入只能经过领域服务。

草稿提交后进入 `Pending Review`，由非申请人的治理角色批准或拒绝。提交和批准都会锁定并
重新计算组织范围、目标快照与提案摘要；目标修改后拒绝批准。批准不创建或修改 ERPNext
标准记录。后续受控执行任务必须按目标 DocType 调用标准控制器，并关联已批准申请。

## 后果

统一模型降低重复治理代码，静态策略防止敏感字段和任意 DocType 写入。审批与执行解耦，
使复核记录稳定、失败可恢复，也意味着批准后仍需显式执行步骤；系统不会把“批准”误报为
标准主数据已经生效。

增加新目标类型或字段必须修改源码策略、测试、目录和版本摘要。策略更新后，旧草稿在提交
时失败关闭并需要重新保存，避免按过期规则批准。

## 验证与退出条件

- 运行时元数据、蓝图、设计目录和数据库索引保持一致。
- 覆盖五类静态策略、未知/敏感字段、类型、Link、必填和停用语义。
- 覆盖组织范围、跨法人、目标漂移、重复待审、乐观修订和幂等冲突。
- 覆盖草稿、提交、批准、拒绝、职责分离、提交后不可变和直写拒绝。
- 真实 HTTP 覆盖 `CORE-016` 至 `CORE-020` 及缺少幂等键。
- 审计和幂等记录不保存字段值、主题、原因或备注原文。

## 迁移与回滚

`bench migrate` 新增三个 DocType、目标类型唯一约束和待审查询索引，不修改标准主数据。
升级前备份站点数据库。回滚应用提交并迁移时保留申请表、子表、域表和数据，不执行破坏性
删除；旧代码不会执行这些申请。

## 安全与合规

治理角色维护领域和审核；`HRP User` 只能创建、修改和查询自己的申请。所有 API 禁止
Guest。动态 SQL 标识符只来自静态策略注册表，业务值使用绑定参数。审计只记录摘要、操作、
修订、数量和字段名；申请值仍按站点数据库访问控制和备份策略保护。
