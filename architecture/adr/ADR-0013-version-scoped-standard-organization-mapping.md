# ADR-0013 以组织版本为范围映射 ERPNext 标准部门与成本中心

## 背景与问题

COD-018 建立了按生效日期发布且发布后不可变的医院组织树。ERPNext 财务和人力业务仍以
标准 `Department`、`Cost Center` 为控制器边界。若把标准引用直接写回组织节点，映射
变化会迫使修改已发布历史；若为每个版本复制标准树，又会破坏 ERPNext 标准主数据连续性。

## 决策驱动因素

- 保持已发布组织版本和节点不可变。
- 保持 ERPNext 对标准部门和成本中心的唯一所有权。
- 支持同一标准目标在不同组织版本中连续复用。
- 防止跨法人、停用目标、重复目标和父子树错配。
- 所有写入必须具备角色、幂等、行锁、乐观修订和脱敏审计。
- 不修改 Frappe、ERPNext 或 Frappe HR，不创建第二个自研 App。

## 备选方案

1. 在组织节点上直接增加标准链接：模型简单，但会污染不可变历史。
2. 每个组织版本复制标准 Department/Cost Center 树：隔离充分，但破坏标准主数据连续性。
3. 只按当前组织编码运行时猜测标准目标：无需存储，但不可审计且重命名后不确定。
4. 建立独立、版本范围、服务维护的映射记录。

## 决策

采用方案 4。

新增只读 `HRP Organization Mapping`。每条记录关联一个发布版本内的组织单元，并可链接
一个 `Department`、一个 `Cost Center`，至少存在其中一个。映射复制法人、医院、组织
编码和类型作为不可变查询上下文。

同一组织版本内，标准目标不得被两个组织单元重复使用；不同组织版本可以复用。启用映射
要求组织单元及目标启用且属于同一法人。若版本内已有相关映射，组织祖先/后代关系必须与
标准 Nested Set 的祖先/后代关系一致。

映射服务不会创建或更新标准记录。所有标准主数据生命周期操作继续调用 ERPNext 控制器。
写服务使用行锁和 `expected_revision`，要求幂等键；查询服务支持直接组织单元或医院、
组织编码和生效日期解析。

## 后果

历史组织版本可以稳定引用标准业务维度，组织调整无需修改旧版本。映射表增加一层显式维护，
但错误关系会在业务使用前被拒绝并可审计。

标准树调整可能使已存映射失效。查询服务会实时复核目标启停和法人；管理员需要先修复标准树
或建立新组织版本映射，系统不会静默猜测替代目标。

## 验证与退出条件

- 元数据、蓝图、目录和数据库唯一约束保持一致。
- 锁定 Bench 覆盖草稿版本、跨法人、停用目标、重复目标和树错配拒绝。
- 覆盖创建、修订冲突、无操作、幂等重放、直接查询和生效日期查询。
- 真实 HTTP 覆盖 `CORE-014`、`CORE-015` 和缺少幂等键。
- 集成角色只能查询，不能维护；直写 DocType 被拒绝。
- 审计和幂等记录不包含标准名称或备注原文。

## 迁移与回滚

`bench migrate` 新增映射表和三个复合唯一约束，不改动标准记录。升级前备份站点数据库。
回滚保留映射表和数据，不执行删除；恢复 COD-019 后可继续使用。

## 安全与合规

仅三个组织管理角色可以维护，`HRP Integration User` 只读。API 禁止 Guest。审计只记录
修订、数量和字段名；备注只以摘要参与幂等指纹。所有 SQL 动态表名和字段名仅来自静态
`Department`/`Cost Center` 注册表，业务值始终使用绑定参数。
