# ADR-0007 使用具体业务台账和公共追加冲销基类

## 背景与问题

预算、科室库存等多个 HRP 领域都需要不可变台账。若每个模块自行处理权限、冲销和并发，
容易出现原记录更新、重复冲销、锁等待和幂等差异；若建立一张以 JSON 承载所有业务的
通用台账，又会丢失字段约束、权限边界、查询能力和领域所有权。

## 决策驱动因素

- 一个自研 App 内的台账必须共享相同安全和事务语义。
- 已记账记录只能追加和冲销，不能修改或删除。
- 冲销必须是可验证的等额反向记录并指向原记录。
- 并发冲销只能成功一次，锁竞争必须快速失败。
- 每个领域仍需要结构化 DocType、字段和权限。
- 写入必须复用 COD-011 领域服务、审计和持久化幂等。
- 不修改 Frappe、ERPNext 或 HRMS，不直接写标准财务和库存台账。

## 备选方案

1. 每个模块独立实现：短期直接，但安全和并发语义会漂移。
2. 建立一张万能 JSON 台账：复用简单，但破坏结构化领域模型和最小权限。
3. 修改 Frappe Document 核心：覆盖范围大，但违反锁定上游和 Press 升级边界。
4. 保留具体业务 DocType，提供公共定义、控制器和领域服务基类。

## 决策

采用方案 4。

`ImmutableLedgerDefinition` 描述具体 DocType 的角色和反向变换。
`ImmutableLedgerDocument` 拒绝服务上下文之外的插入以及所有更新、删除、重命名和取消。
追加与冲销基类继承 COD-011 `DomainService`。

冲销使用原记录行锁和存在性检查，在同一事务中生成反向记录。锁使用不等待模式，竞争
返回受控冲突；原记录已有冲销时拒绝再次冲销。平台只提供只读契约 API，不提供任意
DocType 的通用写入口。

## 后果

具体业务模块需要声明 Ledger 定义并分别建立追加、冲销服务。新增少量样板代码，换取
结构化模型、统一权限和可测试的并发语义。数据库管理员和任意原始 SQL 仍可绕过应用层，
因此生产数据库权限、备份审计和对账不能省略。

COD-012 不创建生产通用台账表，也不改变 398 个设计 DocType。预算和库存台账在各自 COD
中落地。

## 验证与退出条件

纯单元测试验证定义和反向变换。锁定 Frappe/MariaDB 集成测试验证服务专用插入、不可变
控制器、持久化幂等、一次冲销、双连接行锁竞争、异常回滚、脱敏审计和真实 HTTP 权限。
仓库门禁拒绝具体 HRP Ledger 绕过公共服务的直接 Frappe 访问。

## 迁移与回滚

本决策无生产表结构或业务数据迁移。回滚应用提交即可；不得删除后续业务模块已经生成的
Ledger 数据。具体 Ledger 上线和回滚必须由对应 COD 与新变更记录控制。

## 安全与合规

DocPerm 只读，写入角色在幂等预留前校验。审计不记录台账载荷或幂等原始键。
`dimensions_json` 规范化，`source_hash` 校验格式。生产数据库账户应禁止终端用户执行
原始更新和删除，并通过备份、数据库审计和业务对账发现应用层之外的篡改。
