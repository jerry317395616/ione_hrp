# ADR-0018 使用默认拒绝的组织访问范围统一数据权限查询

## 背景与问题

HRP 后续预算、采购、资产、人事和项目模块都需要按法人、医院和科室限制数据。仅依靠角色无法表达组织
边界，而各模块自行拼接 SQL 会产生不一致、注入风险和漏过滤。Frappe User Permission 适合单值链接，
但不足以表达一个已发布组织树节点及其所有下级、按 DocType 和操作区分的组合授权。

## 决策驱动因素

- 任何组织范围缺失或配置错误都必须默认拒绝；
- 角色权限与数据范围必须同时成立，数据范围不能提升 DocPerm；
- 已发布组织树的下级范围必须可确定性展开；
- 所有业务模块应复用同一过滤契约；
- 策略不能执行 SQL、Python、脚本或任意表达式；
- 权限解析必须可审计但不泄漏用户和组织原值。

## 备选方案

1. 只使用角色：维护简单，但无法表达医院和科室边界，会导致角色数量膨胀。
2. 只使用 Frappe User Permission：适合单值 Link，但难以表达版本化组织树下级和按操作授权。
3. 各业务模块自行实现过滤：短期灵活，但容易产生漏过滤、语义漂移和 SQL 风险。
4. 在 `ione_hrp` 中实现统一访问范围模型、结构化解析器和 Frappe 权限 hook。

## 决策

采用方案 4。在一个自研 App 内引入 `HRP Access Scope` 与 `HRP Access Scope Member`。解析器始终先
尊重 Frappe DocPerm，再将当前有效授权按 OR 合并。非管理员没有匹配范围时拒绝；缺少所需组织字段时
也拒绝。管理员可以全局访问，但仍不能超越基础 DocPerm。

过滤结果采用结构化白名单条件，不允许策略配置字段名、SQL、脚本或表达式。组织下级只通过已发布组织
版本的 Nested Set 索引展开。普通用户只能查询自己的决策，管理员代查会留下摘要审计。

## 后果

业务模块获得统一 helper 和稳定 `CORE-001` API。新增模块必须声明组织字段映射并补权限回归，不能只在
页面隐藏数据。范围管理增加了明确的管理员工作量，但避免角色无限增殖并能按用户、DocType、操作和有效期
精细授权。

本阶段的 `masking` 明确为空策略；字段脱敏、供应商自有范围、项目组合、仓库和银行账户等非组织维度将
在各领域任务中扩展，不通过开放式 SQL 配置实现。

## 验证与退出条件

- 两张运行时 DocType、蓝图与设计目录字段一致；
- 无范围、无基础权限、未知操作和字段不兼容均拒绝；
- 组织下级只在同一已发布版本中展开；
- 列表 SQL 条件与单条读取使用同一结构化条件；
- 普通用户不能代查其他用户，管理员代查有摘要审计；
- 真实 HTTP 验证 `CORE-001` 无写入、无需幂等键；
- 当领域专用维度或字段脱敏需要统一扩展时，以新 ADR 复审本决策。

## 迁移与回滚

部署前备份站点数据库。先升级应用并运行 `bench migrate` 创建两张表、索引和中文工作区，再配置范围。
回滚时保留范围和授权明细，不执行破坏性删除；旧版本忽略新表。紧急收权应先停用范围，再回滚代码。

## 安全与合规

Guest 永久拒绝；管理员全局范围仍受基础 DocPerm 限制。过滤字段来自代码白名单和 DocType 元数据，值由
数据库转义。审计仅记录 DocType、操作、决策、范围数量和摘要，不记录用户名、组织值或过滤值。授权配置
由 Frappe 版本审计记录维护，角色与访问范围共同满足最小权限原则。
