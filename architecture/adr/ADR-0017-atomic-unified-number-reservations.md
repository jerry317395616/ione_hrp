# ADR-0017 使用原子序列和不可变预留记录提供统一业务编号

## 背景与问题

医院 HRP 的采购、预算、合同、资产和集成业务需要统一生成可审计编号。仅在各 DocType 中配置
`autoname` 无法表达医院、业务日期和受控维度，也无法向调用方返回稳定预留令牌。使用“查询最大值再加
一”的实现会在并发请求下重复发号；允许管理员编写 Python、SQL 或表达式又会扩大执行权限。

设计目录原有 `HRP Numbering Scheme` 是通用主数据占位模型，包含币种、工作流等无关字段，也没有
持久化编号预留，因此不能满足幂等、不可重用和审计要求。

## 决策驱动因素

- 同一业务编号在全站点永久唯一；
- 同一幂等键重放必须返回同一个编号和预留令牌；
- 不同方案、日期重置分桶和业务维度并发时不得串号；
- 已发编号不得删除、修改或回收；
- 模板必须是声明式白名单，不能执行 SQL、Python 或任意表达式；
- 编号方案必须有组织范围、有效期、乐观修订和完整审计；
- 不修改 Frappe、ERPNext、Frappe HR，也不创建第二个自研 App。

## 备选方案

1. 每个业务 DocType 独立使用 `autoname`：简单，但规则分散且没有统一预留证据。
2. 查询现有最大编号再加一：实现直观，但并发不安全。
3. 调用外部编号服务：可集中治理，但增加网络依赖和跨事务失败窗口。
4. 在 `ione_hrp` 中使用 Frappe `tabSeries` 的事务行锁语义，并保存不可变预留记录。

## 决策

采用方案 4。`HRP Numbering Scheme` 保存方案编码、组织范围、模板、重置周期、流水号位数、起始序号、
有效期、模板摘要和修订号。`HRP Number Reservation` 保存每次发号的编号、预留令牌、日期、维度、计数
分桶、序号、方案修订和审计上下文；记录创建后不可修改、删除或回收。

模板只允许大写字面量及 `{YYYY}`、`{YY}`、`{MM}`、`{DD}`、`{SEQ}` 和
`{DIM:key}`。维度键和值采用固定字符集和数量、长度上限。每个模板必须且只能包含一个 `{SEQ}`，
维度必须与模板完全匹配。

计数器键由方案、重置分桶和规范维度生成摘要。服务使用 MariaDB 的单条
`INSERT ... ON DUPLICATE KEY UPDATE` 原子递增并在同一事务中 `SELECT ... FOR UPDATE` 读取结果。
首次分配与后续递增使用同一并发语义。编号和预留令牌还由数据库唯一约束做最终保护。

## 后果

所有模块可以通过一个稳定 API 取得编号，不再复制编号逻辑。已发编号存在不可变证据，格式变更在首个
预留产生后被禁止；需要新格式时创建新方案。显示名称、启用状态和有效期仍可通过乐观修订更新。

编号预留不等同于业务单据提交。调用方取得编号后即视为已发号，后续业务取消不会回收编号，这会产生
可解释的连续性空洞，但避免历史号码被重用。

## 验证与退出条件

- 运行时 DocType、蓝图和设计目录完全一致；
- 创建、修订、无变化、修订冲突和发号后格式锁定均有测试；
- 月、年、日、永久分桶及维度隔离有确定性测试；
- 幂等重放不新增预留，不同请求产生递增编号；
- 跨方案编号碰撞由唯一约束拒绝并回滚序列和幂等记录；
- Guest、无角色用户、业务用户、集成用户、审计员和管理员权限有测试；
- 真实 HTTP 覆盖方案维护、发号、重放、查询和缺失幂等键；
- 审计只记录摘要、修订、分桶和序号，不记录完整编号和维度值。

## 迁移与回滚

升级前备份站点数据库。`bench migrate` 创建方案表、预留表及命名索引，不迁移或删除 ERPNext 标准
数据。回滚应用版本时保留两张表、`tabSeries` 中以 `IONE-HRP-NUM-` 开头的计数器和全部预留记录，
不执行破坏性删除；恢复新版本后继续使用原序列。

## 安全与合规

Guest 永久拒绝。方案维护仅允许 `System Manager` 和 `HRP System Manager`；分配允许 HRP 业务与
集成角色；普通业务用户只能读取自己创建的预留，审计员和管理员可读取全部。服务在权限校验后才创建
幂等记录，日志不包含编号、维度原文、备注或幂等键。
