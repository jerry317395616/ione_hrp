# ADR-0008 使用事务 Outbox 和消费者范围 Inbox 去重

## 背景与问题

HRP 业务事务完成后需要发布领域事件或同步外部系统。若在事务中直接请求外部系统，网络
超时会占用数据库锁，且远端成功、本地回滚时无法恢复一致性；若事务提交后临时发送，
进程崩溃会丢失消息。至少一次投递又会产生重复消费，重复创建采购、付款或主数据。

## 决策驱动因素

- 业务写入与待发布消息必须原子持久化。
- 外部系统调用不得发生在包含未提交业务写入的数据库事务中。
- 网络投递采用可恢复的至少一次语义。
- 消费者必须按事件身份持久化去重，而不是依赖内存缓存。
- 并发领取必须快速失败，崩溃后的租约必须可恢复。
- 载荷需要确定性序列化、哈希和版本，但审计不得泄露正文或令牌。
- 写入复用 COD-011 的权限、审计、savepoint 和持久化幂等。
- 不修改 Frappe、ERPNext 或 Frappe HR 核心源码。

## 备选方案

1. 在业务事务中直接调用外部系统：实现直接，但产生长事务和双写不一致。
2. 提交后直接发送且不落库：延迟低，但进程故障会永久丢失事件。
3. 仅使用 Redis 队列：适合调度，不提供与 MariaDB 业务事务的原子提交。
4. 通用事务 Outbox + 消费者范围 Inbox，并由具体领域声明服务。

## 决策

采用方案 4。

Outbox 在业务事务中追加 `Pending` 记录。领取使用 `FOR UPDATE NOWAIT`、处理令牌哈希和
有限租约，成功、失败、重试与死信只能经受控领域服务迁移。网络适配器必须在领取事务
提交后运行，因此崩溃恢复可能重复投递，语义明确为至少一次。

Inbox 使用 `SHA-256(consumer + NUL + event_id)` 作为确定性记录名。同一身份和载荷的
已处理事件重放结果；身份相同但载荷不同则拒绝。开始、业务副作用和完成在同一事务，
异常整体回滚。

基类只提供模型、控制器和服务模板。COD-013 不创建通用生产消息表，也不开放任意写
HTTP API。COD-101～103 分别实现外部系统配置、具体 Inbox 和具体 Outbox。

## 后果

系统获得可审计、可恢复和可测试的跨事务消息边界，但传输适配器与消费者必须正确处理
重复事件。队列需要保留、监控、死信处置和对账；这些运营能力由后续 COD 实现。

令牌仅返回给领取者并以哈希落库。载荷和结果按规范 JSON 保存，可能包含业务敏感数据，
因此具体 DocType 必须配置字段权限、保留期、备份和数据库访问审计。

## 验证与退出条件

纯单元测试验证字段、状态、规范 JSON、哈希、确定性名称和令牌。锁定 Frappe/MariaDB
集成测试验证服务专用 CRUD、权限先行、持久化幂等、行锁竞争、租约、重试、死信、
Inbox 去重、载荷冲突、审计脱敏和真实 HTTP 权限。仓库门禁禁止服务提交事务或调用网络
客户端，并固定 `PLT-016` 为只读接口。

## 迁移与回滚

本决策不新增生产表、Fixture 或数据 Patch。回滚 COD-013 应用提交即可。后续具体消息表
上线后，任何回滚必须先停止生产者和消费者，导出未完成消息并由对应变更计划恢复，禁止
直接删除 Outbox、Inbox 或死信记录。

## 安全与合规

具体 DocPerm 只读，角色在幂等预留前验证。事件 ID、令牌、载荷、结果、错误正文和原始
幂等键不得写入应用日志。处理令牌使用恒定时间哈希比对。数据库原始写权限、备份加密、
保留期和访问审计仍由生产运维策略负责。
