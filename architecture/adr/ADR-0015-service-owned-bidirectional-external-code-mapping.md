# ADR-0015 使用服务专属写入和双身份摘要实现外部编码双向映射

## 背景与问题

HIS、财务、供应链等外部系统使用的编码与 ERPNext 标准主数据名称并不相同。集成需要稳定地从外部码
解析到内部记录，也需要从内部记录反查目标系统编码。若把映射散落在各接口代码中，重复、歧义、过期
映射和跨法人错误将无法统一治理。

完整业务身份包含多个最长 140 字符的字段。直接建立复合唯一索引可能超过 MariaDB `utf8mb4`
索引长度限制。单纯依赖应用查询也无法抵御并发写入。

## 决策驱动因素

- 外部编码必须保留前导零和大小写；
- 入站和出站都必须是一对一、确定性、可按业务日期复现；
- 写入必须具备角色、幂等、行锁、乐观修订和数据库唯一约束；
- 目标范围必须与法人、医院、组织版本和静态主数据策略一致；
- 不修改 Frappe、ERPNext、Frappe HR，也不创建第二个自研 App；
- 不绕过 ERPNext 标准主数据所有权。

## 备选方案

1. 每个外部系统维护独立映射表：边界清楚，但模型、权限和审计重复，难以统一反向解析。
2. 在标准主数据上增加外部编码字段：实现简单，但一个记录无法安全承载多个系统和组织作用域。
3. 使用长字段复合唯一索引：语义直接，但存在索引长度限制，迁移可靠性不足。
4. 使用一个受控映射 DocType，并为源身份和目标身份分别生成版本化 SHA-256 唯一键。

## 决策

采用方案 4。

映射归属 `ione_hrp` 的 `HRP Master Data` 模块。`source_key` 和 `target_key` 从完整、规范化的业务
身份确定性生成，并分别建立命名唯一约束。摘要仅用于身份和索引，不替代可读业务字段。

DocType 在 Desk 中只读。创建和更新只能经过 `UpsertExternalCodeMappingService`；查询经过两个方向
明确的只读领域服务。查询必须提供显式生效日期，不使用服务器当天日期作为隐式默认值。

## 后果

并发写入由服务检查和数据库约束共同保护，入站与出站解析都具有明确的一对一语义。新增外部系统无需
增加新表或新 App，但必须遵守同一权限、作用域和审计契约。

身份算法变更属于数据迁移和兼容性变更，必须提升键版本、提供回填并新增 ADR。哈希碰撞概率可以忽略，
但业务字段仍完整保存，发生配置异常时可以重新计算并核查。

## 验证与退出条件

- 运行时元数据、蓝图和设计目录字段完全一致；
- 数据库存在源身份、目标身份两个唯一约束和有效期索引，重复迁移无漂移；
- 覆盖创建、重放、无变化、修订冲突、身份不可变、双向唯一和日期边界；
- 覆盖跨法人、无效医院/组织、停用目标、未知领域和权限拒绝；
- 覆盖 `CORE-004`、`CORE-021`、`CORE-022` 的真实 HTTP 请求；
- 审计日志不包含外部名称或备注原文。

## 迁移与回滚

升级前备份数据库，运行 `bench migrate` 创建新表和索引。回滚应用版本时保留表、约束和数据，禁止
破坏性删除。恢复新版本后无需重新导入映射。

## 安全与合规

Guest 永久拒绝。写角色与只读集成角色分离，角色校验发生在幂等预留之前。所有业务值使用 SQL 绑定
参数，动态标识符来自静态白名单。审计只记录摘要、方向、修订号和字段名。
