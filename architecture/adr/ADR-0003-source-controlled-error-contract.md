# ADR-0003 采用源码注册表和 Frappe 适配器统一错误契约

## 背景与问题

`ione_hrp` 已有 API、安装钩子、服务和 DocType 控制器分别直接调用
`frappe.throw`。调用者只能依赖英文消息和异常类名，无法稳定判断认证、权限、
校验、冲突、策略限制、依赖故障或内部错误，也无法获得可用于支持排障的安全
标识。若错误码由生产 Site 的可编辑 DocType 管理，同一代码版本又可能在不同
站点返回不同契约。

## 决策驱动因素

- 错误码必须跨模块、语言、HTTP API 和后台任务保持稳定。
- 错误消息必须可翻译，业务载荷、凭据、原因链和堆栈不得进入公开响应。
- HTTP 状态、重试语义和日志级别必须由机器校验，不能由每个端点猜测。
- 契约变更必须与代码、测试和 API 目录在同一 PR 中评审。
- 不修改 Frappe 核心异常处理，也不建立生产站点可绕过 Git 的第二份真相。

## 备选方案

1. 继续直接使用 `frappe.throw`：实现简单，但没有稳定机器码和统一响应。
2. 使用 Frappe DocType 管理错误码：界面可编辑，但会产生站点漂移和部署前
   不可验证的双重真相。
3. 使用源码 JSON 注册表、纯 Python 严格解析器和 Frappe 服务适配器：可在
   CI 前置验证，同时保留标准 HTTP 状态、翻译和 Frappe 消息体验。

## 决策

采用方案 3。`ione_hrp/config/error_catalog.json` 是错误定义唯一机器权威，
错误码使用连续的 `IONE-CORE-xxxx` 命名空间。纯 Python 层负责严格解析、
确定性摘要和异常对象；`ione_hrp.services.errors` 负责翻译、Frappe 响应、
安全响应头与脱敏审计。业务代码只能通过该公开服务抛出受控错误，不再直接
调用 `frappe.throw`。公开错误仅包含 schema、code、category、message、
`error_id` 和 retryable。

## 后果

客户端可以依据稳定错误码和 HTTP 状态处理失败，中文消息由标准翻译文件提供。
新增错误必须追加编号并同步测试、文档和 API 契约。服务端脱敏日志只保留原因
类型名称，不保留原始原因消息链；公开响应和应用审计也不保存请求载荷或敏感
标识。完整
请求关联上下文由后续 COD-010 建立，本决策只生成单次错误引用 ID。

## 验证与退出条件

仓库测试必须验证严格 schema、唯一且连续编号、类别与 HTTP 状态映射、重试
语义、翻译覆盖、确定性摘要和禁止直接 `frappe.throw`。锁定 Bench 必须验证
管理员目录查询、Guest/普通用户错误响应、状态码、响应头、脱敏审计及零数据
写入。若 Frappe 提供等价且稳定的应用级机器错误契约，可由新 ADR 取代本决策。

## 迁移与回滚

本决策不创建数据库表、Fixture 或 Patch。迁移只替换 `ione_hrp` 自有调用点，
不改变已提交业务单据。回滚需整体恢复旧调用点、API 目录和注册表；已发布的
错误码不重用，后续变更通过新 COD 和新码追加。

## 安全与合规

错误响应不包含堆栈、原因消息、文件路径、SQL、凭据、患者标识或业务载荷。
审计只记录错误码、随机 `error_id`、HTTP 状态、重试标志和原因类型名称。
错误目录查询只允许 `System Manager` 或 `HRP System Manager`，无 HTTP 写
接口。500 类错误仍由 Frappe 的标准服务端机制按环境策略记录。
