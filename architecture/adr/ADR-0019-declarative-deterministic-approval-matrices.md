# ADR-0019 使用声明式确定性审批矩阵解析审批责任

## 背景与问题

医院采购、预算、人事和资产单据会随法人、医院、科室、金额及业务类型采用不同审批链。仅使用固定
Workflow 无法复用跨模块规则；开放脚本或表达式虽然灵活，却会带来任意代码执行、越权、不可审计和
不可重放的问题。

## 决策驱动因素

- 同一单据上下文必须稳定产生同一审批链；
- 审批策略不能执行用户提供的代码、SQL 或表达式；
- 角色审批人仍须满足目标 DocPerm 与 COD-024 组织范围；
- 策略歧义、空审批人和上下文篡改必须默认拒绝；
- 规则修订需要乐观锁、幂等写入、摘要审计与可回滚数据。

## 备选方案

1. 为每个业务模块单独编写条件分支：短期直接，但重复且难以统一审计。
2. 允许 Server Script 或 Python 表达式：灵活，但攻击面和运行不确定性不可接受。
3. 只使用 Frappe Workflow：适合状态流转，但难以表达跨模块金额和组织策略选择。
4. 在 `ione_hrp` 中实现声明式矩阵解析器，并让 Workflow 或业务服务消费其结果。

## 决策

采用方案 4。矩阵只保存受限结构化字段。选择逻辑由受审代码实现，调用时验证真实单据的组织、日期、
金额和额外维度。最高优先级出现多个匹配矩阵时拒绝。审批人按角色或用户解析，但必须是启用系统用户，
并同时拥有目标单据写权限及组织写范围。

解析器只返回审批责任，不执行批准、不改变目标单据。业务流转继续使用 Frappe Workflow 或后续受控服务，
从而分离“谁应审批”和“如何改变状态”。

## 后果

各模块获得稳定的 `CORE-002` 决策契约，策略可在中文 Desk 中维护并按修订追踪。配置人员不能编写任意
逻辑，复杂条件需显式扩展经过评审的维度白名单。审批链发生歧义或没有合格审批人时，业务会停止并要求
修复配置，这符合财务与人事控制的默认拒绝原则。

## 验证与退出条件

- 运行 DocType、蓝图、目录、工作区、索引和 API 契约一致；
- 阈值、并行会签、摘要稳定性和非法维度有纯测试；
- 真实 Frappe 测试覆盖幂等、乐观锁、权限、组织范围、歧义和 HTTP；
- 任何脚本、表达式、开放 SQL 或绕过真实单据的实现均被仓库契约拒绝。

## 迁移与回滚

部署前完整备份站点；迁移新增矩阵主表、步骤子表和索引。回滚时保留新表，旧代码忽略其数据。紧急情况
优先停用矩阵；禁止以删除表作为回滚方式。

## 安全与合规

维护权限仅授予 System Manager 和 HRP System Manager，HRP Auditor 只读。业务用户只能调用只读解析器。
审计记录策略摘要、修订、步骤数和审批人数，不记录审批人、组织值或业务维度原值。
