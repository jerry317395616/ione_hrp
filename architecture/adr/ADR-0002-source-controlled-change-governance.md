# ADR-0002 以 Git 中的 ADR 和变更记录作为工程治理权威

## 背景与问题

架构决策必须在代码合并和数据库迁移之前可评审、可追溯。若把 ADR 或工程变更
只存入生产 Site，CI 无法在构建前验证，数据库又会成为与 Git 冲突的第二份
真相。纯自由格式 Markdown 则无法稳定校验状态、关联任务、风险和回滚证据。

## 决策驱动因素

- 决策必须与实现、测试和回滚计划在同一 PR 中原子评审。
- CI 需要在没有生产数据库和凭据的环境中完成验证。
- 破坏性、权限、上游基线和单应用边界变更必须失败关闭。
- Frappe 管理员仍需要查看当前治理状态，但不能绕过 Git 修改决策。

## 备选方案

1. 使用 Frappe DocType 保存 ADR：界面友好，但构建前不可用且产生双重真相。
2. 仅使用自由格式 Markdown：易写，但状态、风险和任务关联无法可靠自动化。
3. Git 中使用严格 ADR front matter、结构化变更记录和机器策略：可在 PR/CI
   前置验证，同时保留可读文档。

## 决策

采用方案 3。`architecture/adr` 保存带严格 front matter 的 ADR，`changes`
保存每个已实施 COD 的结构化记录，`ione_hrp/config/change_governance.json`
定义状态机、风险等级和受保护路径。Git 分支、PR、CI 和提交历史是唯一写入与
审计通道。Frappe 只提供 System Manager 可读的脱敏状态 API，不提供 HTTP
写入、批准或状态转换接口。

## 后果

所有已完成任务都必须有变更记录；一个 PR 只能声明一个 COD，变更文件必须被
该记录的路径范围覆盖。受保护路径和破坏性变更需要 Accepted ADR。重复校验
产生相同摘要，不依赖生产 Site。维护者需要同时更新任务文档、变更记录和必要
的 ADR。

## 验证与退出条件

仓库契约、单元测试和锁定 Bench 集成测试必须验证严格解析、状态迁移、风险
升级、权限、异常路径、确定性摘要和只读 API。若未来采用具备同等 Git 原生
审计、离线 CI 和失败关闭能力的治理平台，可由新 ADR 取代本决策。

## 迁移与回滚

本决策不创建数据库表或 Patch。现有 COD-001 至 COD-007 以结构化记录补齐
基线；回滚代码只移除门禁和只读 API，不改变生产数据。已经合并的 Git 历史和
PR 审计不删除。

## 安全与合规

治理 API 不返回仓库绝对路径、文件正文、用户名、令牌或提交命令输出。变更
记录不得保存凭据和业务敏感数据。权限限制为 `System Manager` 或
`HRP System Manager`；普通用户和 Guest 必须被拒绝。
